4. How a person would get a Foundation row

Client INSERT into public.users is intentionally forbidden. Migration 0001 creates trigger on_auth_user_created on auth.users calling handle_new_auth_user(), which inserts the matching public.users row. A leftover commented duplicate of that trigger sits underneath — noise, not a second path.

A prior engineer note (docs/audit/06-schema.md) said this trigger was only a commented sketch. That note is stale. In the current 0001 file the trigger is active in the drawing. What remains true: the running app never creates public.users rows, because it never talks to this database. Nearly every other table foreign-keys to users(id). Connecting screens to Supabase without this bootstrap working would fail the first real write.

Generated TypeScript database types (src/integrations/supabase/types.ts) are still an empty stub. Providers cast past the type checker. A misspelled column would not fail Inspections; it would fail at runtime against a live project.

7. Live storage map (what actually holds water)

Twenty-four-plus keys, all device-local. See Document 01 for the ownership table. Nothing in src/pages should write these keys except through the owning module. Community, documents, and some profile writes now go through the service seam, which in local mode still ends in the same keys.

8. Cross-provider consistency

Re-checked against current providers: each table is owned by one domain’s TypeScript provider (profile + profile-directory both read profiles / district_profiles with compatible partial shapes). No two providers fight over the same columns. Every .from("…") / .rpc("…") name in those providers resolves to a table or function the migrations create. exchange_listings in dead src/data/listings.ts is the exception — it is not in the Foundation at all.

9. Foundation verdict

Blueprint quality vs pour status

This is a serious Foundation drawing: 29 tables, function-mediated writes, privilege hardening through 0020, SQL tests sitting beside the migrations. It is not a live basement. Pouring it is a later, explicitly approved step — and it cannot be poured “as the product” until the field gaps in §6 are either added to the drawing or accepted as product reductions, and until screens are actually framed onto the seam (Document 01 §7).
